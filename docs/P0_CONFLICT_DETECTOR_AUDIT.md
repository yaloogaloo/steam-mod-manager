Evidence files:

---

## 1. Current real conflict definition

Automatic path detection has **one** rule:

> If two or more **enabled** Mods that **exist in `mods`** list the **same**
> `Path.expanduser().resolve()` string as a deploy **target** in
> `.info/deploy_manifest.json`, that target is `FILE_OVERWRITE`.

Then:

```
FILE_OVERWRITE  OR  user-declared RELATIONSHIP
        ↓
ConflictReport.status = conflict_status = "conflict"
        ↓
update_mod_status(...)   if persist=True
        ↓
UI badge / Resolve Conflict
```

That is **target-path identity**, not a game conflict, not an identity conflict,
and not a dependency conflict.

---

## 2. FILE_OVERWRITE trigger (exact)

| Input | Used? |
|---|---|
| `deploy_manifest.json` `files[].target` | **Yes** |
| `Path.resolve()` equality | **Yes** — rule `FILE_OVERWRITE.identical_resolved_target` |
| Source file names / hashes | No |
| Load order / deploy order | No |
| Base vs patch / compatibility patch | No |
| Game-specific loading (Anno stamps, Pak, UE mods) | No |
| User accepted overwrite | No |
| `mod_relationships` | Separate `RELATIONSHIP` / `GAME_RULE_CONFLICT` only |
| Folder names / titles | No |

`len(owners[resolved_target]) >= 2` → one `ConflictEntry` per target, attached to **every** owner.

Same directory, **different** filenames: **not** a conflict. `PAK_OVERLAP` is documented as legal and is **not generated**.

## 3. Classification inventory (actual semantics)

| Label | Generated by ConflictDetector? | Persistent `conflict_status`? | Real meaning |
|---|---|---|---|
| `FILE_OVERWRITE` | **Yes** | **Yes** (`conflict`) | Identical resolved deploy target |
| `PATH_OVERLAP` | **No** (only mapped from dead `PAK_OVERLAP`) | No | Enum / UI string only |
| `IDENTITY_CONFLICT` | **No** | No (different column) | Library `content_status=identity_conflict` (two folders, one mod_id) — **not** this detector |
| `DEPLOYMENT_CONFLICT` | **No** | No | Unused enum |
| `DEPENDENCY_CONFLICT` | **No** | No | Unused enum |
| `GAME_RULE_CONFLICT` | Only via `RELATIONSHIP` | Yes if persist | User-declared `mod_relationships` |
| `UNKNOWN_CONFLICT` | **No** | No | Unused |

UI still has translations for IDENTITY_CONFLICT / PATH_OVERLAP. That does **not** mean the detector produces them.

## 4. warn vs conflict (diagnostic upgraded to persistent state)

`ConflictDecisionTrace` is hardcoded:

- `severity = "warning"`
- `decision = "warn"`

`check_all_mods` then:

- `status = CONFLICT_STATUS_CONFLICT`
- `update_mod_status(..., conflict_status=conflict)`

This is the smoking gun: **overlap diagnostic is persisted as a hard conflict.**
Not a UI bug.

---

## 5. Why Resolve Conflict comes back

Call chain:

```
UI Resolve Conflict / flag off
  → update_mod_status(conflict_status=none)
        ↓
later: deploy success
  → _schedule_post_deploy_conflict_scan (daemon)
  → check_all_mods(persist=True)
        ↓
unconditional overwrite of conflict_status
```

Opening the detail panel uses `check_mod(..., persist=False)` and does **not** rewrite DB.
The rewrite is **persist=True** callers, mainly **post-deploy scan**.

There is no “user accepted this overlap” bit. Adding `user_ack` would hide a wrong model.
This audit does **not** add that field.

Production Anno snapshot (readonly, 2026-09-02):

| entity | enabled | conflict_status | last_check_time |
|---|---|---|---|
| 0360 全产业模板 | 1 | **none** | 09:51:36Z |
| 0362 布局模板 | 1 | **conflict** | 09:51:29Z |

Both still overlap 141 resolved targets. Asymmetric DB state is consistent with **manual clear of one row** plus **no later full persist scan** (or a scan that did not complete both). The mechanism can and will rewrite `none` → `conflict` on the next `persist=True` pass.

## 6. Anno 141 paths — what it means

Readonly: `data/p0_anno_conflict_forensics.json`

| | 0360 | 0362 |
|---|---|---|
| Sidecar workspace_id | `17863520439005318` | `17863521013284165` |
| DB workspace_id | empty | empty |
| Manifest files | 515 | 167 |
| Resolved overlap | **141** | **141** |
| `mod_relationships` | none | none |
| Load-order / patch fields | none | none |

141 identical resolved **deploy targets** means both last deployments claimed the same stamp/file paths. For Anno layout templates that is often **intentional overwrite** (two blueprints writing overlapping stamps).

The detector **cannot** know that. It only knows path identity. **141 is not proof of a harmful conflict.** It is proof of overlap.

Workspace IDs in sidecars are distinct; they are **not** IDENTITY_CONFLICT. DB `workspace_id` is still empty (sidecar/DB drift). Polluting Steam `source_url` on these internals is a P0-5 URL scrub issue, frozen this round.

---

## 7. Business-semantics verdict

**FILE_OVERWRITE does not have enough business meaning to be a persistent conflict.**

It answers: “did two enabled, in-DB Mods last deploy to the same absolute path?”

It does **not** answer: “will the game break?”, “is this a patch?”, “did the user want this?”

---

## 8. Schemes A / B / C

### A — keep auto conflict, add real rules

Would need load-order, game load rules, base/patch metadata, deploy order. **Those inputs do not exist in this codebase.** Implementing A now would invent rules.

### B — FILE_OVERWRITE / PATH_OVERLAP as diagnostic only

Keep traces, preview, overlap counts. **Do not** auto-write `conflict_status`. Persist only:

- user-declared `RELATIONSHIP`
- explicit user mark as conflict

Matches the trace (`decision=warn`) and the Anno case.

### C — delete automatic path detection

Preview before deploy would disappear. Overlap evidence is still useful. **Too early.**

### Recommendation (not executed)

**B.** Evidence: Path.resolve-only rule; warn/conflict contradiction; user clear rewritten; Anno 141 overlap with no game rule; no load-order anywhere in conflict.py.

**This round did not implement B.**
